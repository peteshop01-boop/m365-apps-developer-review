# Questions about how the project should run

## What went wrong that reviewers should test

The owner reports roughly two months of work without the first verified installed private Save. That is the owner's account, not an audited labour total. There is substantial code and historical testing, but versions, configuration and installation do not consistently join into one accepted result.

The supplied evidence describes narrow checks finishing without the next ready task starting; later-feature work while Save remained unfinished; repeated handovers; source review being mistaken for delivery; and tool/browser/script incidents being reported without clearly separating their effects. These are observations to challenge, not a conclusion that every control or all AI-assisted work is useless.

## A proposed operating model for review

One delivery owner maintains the next usable outcome. Builders implement and run relevant developer checks. Independent reviewers challenge changed security/technical behaviour without certifying their own code. QA verifies the exact installed TEST candidate. The business owner tests the agreed journey and separately authorises LIVE release.

An approved objective continues across its ordinary subtasks. A specialist returning does not finish the PM's delivery objective. The next safe, already-authorised step should start, or the PM should identify one exact unmet condition and the person/action that resolves it. An activity badge or saved prompt is not proof of useful work.

Keep tasks large enough to deliver a coherent slice, small enough to verify and recover. Do not rebuild unchanged evidence or create new agents merely because an action number changed. Reuse healthy specialists, preserve a single source writer and keep handovers compact. Never bypass platform controls, silently broaden permissions or replace a failed check with fabricated evidence.

These are adopted project practices informed by the team's training and experience. This pack does not reproduce proprietary course content or claim endorsement by a training provider.

## Suggested first-Save delivery sequence, not an agreed new sprint baseline

| Phase | Concrete result | Completion proof |
|---|---|---|
| 1. Reconcile | One chosen source candidate and exact missing connections | File/function evidence and a small task list |
| 2. Configure private TEST | Correct fictional identities, records, fields and permissions | Ordinary-owner/unrelated-account and recovery evidence |
| 3. Connect and validate | Real Save path and focused tests | Executed results for the exact source; failures retained |
| 4. Install | Checked app/workflow available in TEST | Source/package/installed-version mapping |
| 5. Accept | Save, close, reopen, edit and deny unrelated access | Numbered QA and business-owner results |

KPI's complete private sprint/requirement control register is not part of this export. This summary does not renumber or replace either project's approved plan.
