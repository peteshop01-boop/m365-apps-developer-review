# Actor-scoped Standard storage boundary — SOURCE ONLY / runtime Held

`src/processor/ActorScopedProcessor.ts` composes the existing `StandardExpenseProcessor`, `SharePointStandardStore` and `SharePointRequestReader` through the used `IStandardStoreIO` interface. It emits/validates real SharePoint REST operations against an injected protected Standard-action boundary. It supplies no network connection, credential, hosting service, activation flag or tenant permission. **It is not a Node/Azure hosting proposal and does not execute inside a cloud flow as TypeScript. The existing WDL still needs the equivalent guards and folder writes before it can replace the held fixed-claimant candidate.**

The request's native Author selects an ordinary Microsoft user and one globally queried protected active roster row. A command actor, email, fixed parent or browser-selected folder cannot supply that identity. The same shared resource bindings work for A/B/C and other approved employees; parent/month is verified against the actor's unique Draft. Completed historical replay uses its explicit saved parent, not a new Draft.

Protected onboarding must supply a separately qualified plain-Note roster field (candidate binding `D01PrivateScopes`) containing all six private folder identities, keyed `requests`, `operations`, `results`, `expenses`, `claims`, `people`; each value has numeric folder item `id` and GUID `uniqueId`. **That field and those folders are not asserted to exist in TEST.** The current native Claims list is empty/inherited with folder creation disabled, so it cannot satisfy admission. No hidden default, schema change, row, grant or folder creation is performed by this adapter. Missing/partial/changed registry refuses the operation.

The immutable deployment policy pins nine dedicated TEST GUIDs/roots, exact role IDs and both permission words, approved recovery, restricted processor roles and native ancestor Limited Access entries. Ordinary content access at a sensitive root is rejected. Private folders require unique exact recovery/processor/employee ACLs; outputs give the employee Read only, requests Read/Add only. Every child must inherit its exact pinned folder; audit remains private at its qualified root. Processor profiles retain EnumeratePermissions/read dependencies, never ManagePermissions/ManageLists/delete. **The ordinary browser composition is unchanged and receives no ACL-enumeration rights. Its matching ancestry integration is still OPEN.**

Creation uses `AddValidateUpdateItemUsingPath` in the verified destination, not root creation followed by movement/sharing. An explicit native field/type map supplies form values; every acknowledgement, error, returned ID, native processor Author and unique-key readback must agree. Native unique-index metadata and the distinct reason/no-required-Category contract are checked before publication. Optional empty plain Notes may round-trip as null; IDs and numbers do not gain that exception. There is no automatic POST retry or permission repair. Lost acknowledgement retains Pending and reconciles the same operation/item.

All store reads, conditional updates, receipt bytes, duplicate/history recovery and terminal publication use the scope wrapper. Final verified completion rereads the canonical request, ledger/result, expense/receipt and audit record including genuine Author, Created stamp, linkage and child permissions. These sequential REST checks do not claim an atomic transaction against later privileged administrative changes. Native change control and actual two-user raw denial remain mandatory.

These tests do not prove Microsoft connector execution, native folder/form-value compatibility, current schema/ACLs, entitlement, actual receipt persistence or Sponsor UAT.

The fake server's raw access now uses the same principal/role-mask snapshots as its REST ACL responses, including group membership, physical root/folder inheritance and explicit unique-item scopes. Root audit entries use their actual root ACL even when they carry business actor attribution; that attribution cannot invent a folder grant. Forging a business owner field cannot grant raw access. An unqualified extra Read grant deliberately exposes a fake row and makes processor verification fail; the model must not fabricate403 for a grant that would allow access. All fixture actor/processor/recovery IDs are synthetic, never deployment bindings or native privacy proof.
