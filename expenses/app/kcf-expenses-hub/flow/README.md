## Integrity and recovery

SharePoint stamps Author; no browser actor is accepted. File size/version/Editor/ETag are checked before and after binary read. Parsed request and canonical immutable request bytes must agree. Parent owner, month, active employee, current nominal and exact195 master are checked; parent CAS carries Creating/Rejecting reservation. Expenses have unique actor-operation provenance. Attachment POST is binary/no-overwrite, then names and full base64 bytes are compared before completion. `clientSha256`/fingerprint are client claims, never authentication; the application independently recomputes receipt hash on bounded readback. The cloud flow compares the actual full stored bytes rather than pretending Standard WDL provides SHA-256.

One parent checkpoint atomically updates totals/version once. Immutable result and audit are verified; terminal ledger and release are read back. Explicit retry policy is none for all connector actions. A timeout never means success: the same sealed request can be operator re-driven and reconciled. Automatic durable re-drive scheduling is **not implemented**; the trigger alone does not promise eventual completion after throttling/outage. Changed/ambiguous data holds Pending; no new operation is substituted. Full completion after source-only checks is not claimed.

## Release gate

The trigger declares `runtimeConfiguration.concurrency.runs=1`. This one qualified processor flow must be the only writer; resubmission must use the same serialized flow. Parent CAS alone does not make overlapping same-operation runs safe to recreate audit evidence. At degree1 Microsoft documents only11waiting runs and a100item SplitOn limit; additional triggers are not guaranteed to start. Immutable request files remain available for explicit protected same-request re-drive, never a new Save operation. This is a one-employee fixture candidate, **not proved24-user throughput**. No unsupported maximumWaitingRuns override is emitted. Native serialization (including manual resubmission) must be verified before enable; the local scheduler merely models the declared setting. A second flow/writer or bypassed serialization invalidates admission. [Microsoft limits](https://learn.microsoft.com/en-us/power-automate/limits-and-config).

Recovery rechecks the immutable audit on every Completed replay, including its private inheritance, processor author, event/time and exact operation/request/actor/parent/expense/record. Missing or changed audit holds without recreating it. Only a Rejected result may normalise a native null multiline `RecordJson` to empty; Completed records remain exact nonempty JSON.
